# CrowdyPy agent guidance

CrowdyPy is the public Python SDK for Crowded Kingdoms. Its API surface follows CrowdyJS
(the flagship) the way CrowdyCPP does; its replication hot path is CrowdyCPP's native core,
vendored and bound with nanobind. Trust the code over this file when they disagree, then fix
this file.

## Branches and tiers

GitHub default is **`prod`**. Work lands on `dev` through a pull request; `test` and `prod`
take merge-forward promotions (`dev` -> `test` -> `prod`) that an admin merges. Nobody can
push to the three branches directly, the admin included (`GH013: Repository rule violations
found` is the rule working). Dependabot targets `dev`.

**TIER ALIGNMENT (hard rule).** A CrowdyPy branch may only pin CrowdyJS and CrowdyCPP
commits that exist on the **same** tier branch of those repos (`dev`<->`dev`,
`test`<->`test`, `prod`<->`prod`). `scripts/ci/check_pin_tiers.py --from-ref` enforces it
in CI against the pull request's base. A promotion of CrowdyPy therefore waits for CrowdyJS
and then CrowdyCPP to reach that tier with the pinned commits.

**Identity surface.** A PR that touches the paths CODEOWNERS lists under `src/crowdypy/`
(auth, portal, pkce, session, auth_state, and their generated `_sync` twins) runs the Cursor
`security-review` subagent first, and the PR body carries its findings.

**Public repository.** Nothing internal goes in: no internal repository names, hostnames,
ports or environment variables. `scripts/ci/check_content_policy.py` scans the tree and the
built wheels and sdist against a denylist. Of the replication server, only the wire format
and the client authentication sequence are public.

## Pins

`pyproject.toml` records everything this tree was made against: `[tool.crowdypy.crowdyjs]`
(version and commit), `[tool.crowdypy.crowdycpp]` (version, tag, commit and the sha256 of
the vendored tree), `[tool.crowdypy.graphql]` (hashes of `schema.gql` and `operations/`) and
`[tool.crowdypy.published-sdl]`. CI re-derives each from the pinned commit, so a hand edit
anywhere downstream of a pin fails.

Moving the CrowdyJS pin (it must be on the same tier branch):

```bash
python scripts/schema_sync.py --crowdyjs ../CrowdyJS --ref <commit>   # schema, operations, pin
python scripts/codegen.py && python scripts/unasync.py
python tools/parity/parity.py --crowdyjs ../CrowdyJS --write docs/parity-matrix.md --strict
```

then port what changed, refresh `tests/fixtures/` from the same commit, and classify or
cover every new difference. `tests/unit/test_fixture_provenance.py` holds each copied fixture
to its CrowdyJS source, and `exec-client-frames.json` and `voice-frames.json` to the vendored
CrowdyCPP copies too. Build CrowdyJS at the new pin (`npm ci && npm run build`) and run
`node tools/fixtures/player_host.mjs ../CrowdyJS`: it rewrites the player-host schemas and
their fixture, and `tests/unit/test_player_host.py` refuses either one from another commit. Moving the CrowdyCPP pin:

```bash
python scripts/vendor_crowdycpp.py --crowdycpp ../CrowdyCPP --ref <tier>/vX.Y.Z
```

CrowdyCPP's own CrowdyJS pin must equal CrowdyPy's (`--check` refuses otherwise).

## The default origin

`src/crowdypy/_default_origin.py` is generated per tier by the operator tooling and never
hand-edited: `dev` declares `dev`, `test` declares `test`, `prod` declares `prod`, so a
client built with no origin dials the tier its wheel was released for. **A promotion can
rewrite this file with no conflict and no mention**: git resolves a one-sided change
silently, so a clean `dev` -> `test` merge can carry `dev` onto `test`. Regenerate it for
the destination tier after every promotion. CI's `scripts/ci/assert_default_origin.py
--from-ref` judges the pull request base, the release guard judges the tag's tier, and the
release re-reads the published wheel.

## Gates

CI (`.github/workflows/ci.yml`) runs all of these; run them before pushing. CI's `mypy` runs
without the project installed (`uv sync --group dev --no-install-project`), so it follows
imports into the generated `_sync/` and checks it too; an editable install hides that, so
reproduce CI's run in a venv of its own (`UV_PROJECT_ENVIRONMENT=/tmp/lint uv sync --frozen
--group dev --no-install-project`, then `uv run --no-sync mypy` with the same variable).

```bash
ruff check . && ruff format --check . && mypy
pytest tests/unit
python scripts/vendor_crowdycpp.py --check
python scripts/schema_sync.py --check
python scripts/codegen.py --check
python scripts/unasync.py --check
python tools/parity/parity.py --crowdyjs ../CrowdyJS --check docs/parity-matrix.md --strict
python scripts/ci/check_content_policy.py
python scripts/ci/check_pin_tiers.py --crowdyjs ../CrowdyJS --crowdycpp ../CrowdyCPP --tier dev
```

The parity gate is **strict** (since 0.4.0): every difference from CrowdyJS carries a
reviewed classification (`native-equivalent` or `browser-exclusion`), a stale or missing one
fails, and a `portable-gap` fails the build. Since 0.40.0 it also reads CrowdyJS's fleet
session (`src/fleet/session.ts`, outside the directories CrowdyCPP's gate reads). Something new in CrowdyJS that CrowdyPy lacks is
ported in the same change that moves the pin; it is not parked as a gap.

The gate reads a CrowdyJS class field initialised with `=` (`readonly profile = new Relay()`)
as a member named `profile`. On the Python side only methods and properties are members; an
attribute set in `__init__` to one of CrowdyPy's classes contributes its methods as
`profile.get` and so on, never `profile` itself. Port such a field as a read-only property, as
`PlayerKit`'s stores are (0.14.0).

## Live e2e

`tests/e2e/` holds black-box suites over the `CROWDY_E2E_*` variables CrowdyCPP's suites read;
unconfigured they skip. Run them against the local stack and then the dev tier before a
release moves on, and record the run in `docs/e2e-coverage.md` (configuration, the
`tools/e2e/provision.py` helper and where each tier's org admin credentials live are there).
`test_e2e_idle_release.py` (slow) lowers the e2e app's idle timeout to 60 s and puts the app's
own value back in a `finally`; an interrupted run can leave it at 60 s, so check
`effectiveIdleTimeoutSeconds` before blaming a release for idle disconnects.

## Idle release (0.25.0)

The replication server (v0.44.0) releases a session that sends no gameplay input for the app's
idle timeout, with `COMMAND_SESSION_RELEASED` reason 5. CrowdyCPP verifies and handles it, and the
connection reports `ConnState.INACTIVE` (6), which nothing reconnects; a game calls
`client.udp.connect()` on the player's next input. Status rows carry the state as a number, so
`ConnState` must name every value CrowdyCPP's `replication::ConnState` has or `ConnState(...)`
raises. Since 0.29.0 (CrowdyCPP 0.81.0) a capabilities message carries the assignment's control
nonce and a v0.45.0 server sends the bound 44/45 forms: a test that wants a final bound release reads
the nonce from the client's CLIENT_CAPABILITIES (`test_replication.py`, `bound_release`). Since
0.27.0 (CrowdyCPP 0.79.0) an idle release within `idle_release_guard_ms` (60 s) of
the client's own gameplay input reconnects instead (a captured release frame verifies again);
a test that wants a final release teaches the fake server the address with a heartbeat, not an
actor update.

## Email confirmation (0.26.0)

ck-api v2.65.0 refuses a gameplay token to a password account made since 2026-11-11 until it
confirms its email (`EMAIL_CONFIRMATION_REQUIRED`). `is_email_confirmation_required_error`
(`domains/portal.py`) mirrors CrowdyJS's `isEmailConfirmationRequiredError`, and
`auth.resend_confirmation_email` is the remedy. The live e2e suites sign up with the tier's
provisioning token, which the gate does not ask, so they need no change.

## Fleet sessions (0.40.0)

One realtime session an organization's game server opens for itself and carries its players on
(Application API v2.89.0, realtime servers v0.50.3, ck-exec 0.25.0 for the hub connection;
CrowdyJS 18.40.0, CrowdyCPP 0.94.1). An org token and a fleet token are server-side credentials:
nothing here may put one on a player's device, in a log line or in a repr.

0.40.0 vendors CrowdyCPP 0.94.1 because 0.94.0 never left dev: a CrowdyPy promotion needs the
pinned CrowdyCPP version tagged on the target tier. 0.94.1 changes no API: its four fleet
documents moved from the headers to its generated operations, and the vendored `src/` is
byte for byte 0.94.0's.

- **The Application API.** `client.fleet_sessions` (`domains/fleet_sessions.py`, async source, so
  `scripts/unasync.py` generates the blocking one) and `exec.server_endpoint` /
  `exec.connect_as_server`. `exec_gateway.py` holds both connections by hand: `call_as`,
  `call_as_raw`, `open_as_server`, `is_server` and the `ExecCallAs` frame (`0x05`, held to the
  shared `exec-client-frames.json`). `_server_only.py` is CrowdyJS's `src/server-only.ts`: the five
  calls refuse before any request where Python is not a server (`sys.platform` `emscripten`,
  `android`, `ios`). The SDK still wraps no `mintManagedPlayerToken`.
- **The binding.** `native/fleet_binding.cpp` binds CrowdyCPP's `replication::FleetSession` under
  the performance rules below. `FleetConfig::reassign` stays unset, so the network thread asks
  Python for nothing and a move is read from `move_ordered`. A carry has no native callback: its
  result is a row of a later batch, like a release (52), a session release (28), a named refusal
  (254), an error (3) and a status (255). `FleetBatch` is a `NotificationBatch`'s columns plus
  `listed`, `recipient_offsets` and `recipient_ids`.
- **The facade.** `src/crowdypy/fleet.py` holds `AsyncFleetSession` and `FleetSession` by hand, as
  `replication.py` holds a player's two connections. It keeps no token in a Python attribute (a
  test reads `vars(fleet)`). CrowdyCPP acts on a `FLEET_CARRY_RESULT`, and reports a carry nothing
  answered, inside `poll()`, and a silence queues no event. So an awaited `carry` polls every 50
  ms while it waits, the asyncio reader wakes once a second with nothing to read
  (`_HOUSEKEEPING_S`), and the blocking session relies on the game's `poll()` every tick. A test
  that answers a carry polls before it expects the session to have acted on the answer.
- **`MIN_SILENCE_TIMEOUT_MS` is CrowdyCPP's own (3,000) since 0.41.0.** 0.40.0 raised a shorter
  timeout to 4,500, because CrowdyCPP 0.94 never counted a silence at 3,000 to about 3,300 ms.
  0.95.0 passes at every value from 3,000 (between the timeout and one capabilities interval
  later), so the facade passes the option through and adds no floor. Do not add one back.
- **Differences from CrowdyJS's `FleetSession`**, each classified in the parity matrix (the gate
  reads `src/fleet/session.ts` since 0.40.0, `FleetSession` against `AsyncFleetSession`): ids are
  `int`, no automatic actor heartbeat (`forgetActor`), `state` for `status`, no `tick` or
  `settled`. `carry_nowait`, `send_actor_updates` and the `send_refused` handler are CrowdyPy's
  and CrowdyCPP's own. The table limit is CrowdyJS's since 0.41.0 (`table_limit`, `TABLE_FULL`).
- **A player's connection** gained what CrowdyCPP 0.94.0 added to the types already bound:
  `Notification.verified`, `wrong_app` and `unsigned_notifications` in `stats()`, and `ERRC`
  through `NotCarried` (`register_replication` loops to the last `Errc`: move it when CrowdyCPP
  adds one).
- **Tests.** `tests/unit/test_fleet_session.py` runs both sessions against a fake realtime server
  (`QUIET` switches the silence timeout and the periodic capabilities off; two tests wait about
  3 s each for a silence), `test_fleet_wire.py` holds the codec to CrowdyCPP's golden bytes, and
  `domains/test_fleet_sessions.py` covers the calls and the refusals.
- **Benchmarks** (`benchmarks/README.md`). A batch row for a carried player costs about 1.1x a
  player's connection's. The two findings 0.40.0 recorded against CrowdyCPP 0.94 are closed by
  0.95.0 (the latest re-check there has the numbers): section 2's receive rate is back, and
  `disconnect()` returns while datagrams still arrive. Section 2 still stops its blaster before
  it closes, so that the number is the receive path's alone.
- **The live suite** (`tests/e2e/test_e2e_fleet_sessions.py`, runs in `docs/e2e-coverage.md`)
  reads `CROWDY_FLEET_API_URL`, `CROWDY_FLEET_APP_ID` and `CROWDY_FLEET_ORG_TOKEN` (a
  module-level `E2E_REQUIRES` replaces the `CROWDY_E2E_*` four in `conftest.py`). Its hub step
  needs `CROWDY_FLEET_HUB_APP_ID`, an app of the same organization with a hub, and the hub's
  node type, key and method (below). It first ran live on 2026-11-27, on dev, for 0.41.0
  (`arena` / `m1` / `state`); it has not run on test or prod. A `CROWDY_FLEET_HUB_*` variable
  left in the shell from another run fails the step with the Application API's refusal, so
  unset them first.
## CrowdyCPP 0.95.0 (0.41.0)

0.41.0 vendors CrowdyCPP 0.95.0 (`dev/v0.95.0`, 3836244) with the pin at CrowdyJS 18.41.0
(`dev/v18.41.0`, 2388502), for Application API v2.90.0, realtime servers v0.51.0 and ck-exec
0.26.1. CrowdyCPP's `MIGRATION.md` 0.95.0 entry and the "A player's connection (0.95.0)" section
of its `AGENTS.md` are the list of what changed; read them before a change here.

- **A refused keepalive is two rows.** `kNotPresentRow` (253) and `kNotPresentEndedRow` (252)
  are the connection's own rows, like the status row (255) and the fleet session's named
  refusal (254): the wire never carries them. The row has the actor in the uuid column, the
  chunk, the first refused keepalive's sequence, and `extras` (verified, the carried player's
  game token id or 0, the end's reason or 0). `NotificationBatch::match` skips every row type
  from 252 up, because a not-present row carries a sequence and an actor as an echo does. A
  new own row takes a number below 252 and moves that bound.
- **Handlers.** `not_present(report)` and `not_present_ended(report, end)` take an
  `ActorNotPresent`, never a `Notification`, and the second takes two arguments, so
  `subscribe`'s handler type is `Callable[..., Any]`. `any` is for what the server sent
  (`_OWN_ROWS` in `replication.py`). The fleet session's `generic_error` handler keeps its two
  arguments, `(notification, verified)`: CrowdyJS passes `keepalive` third, and a third
  positional argument would break every handler written for 0.40.0, so it is
  `notification.keepalive`.
- **With a world session attached** the session owns the connection's handlers:
  `session_binding.cpp` forwards `WorldSessionConfig::onNotPresent` and `onNotPresentEnded`
  into the connection's rows, so `session.on("not_present", ...)` and `client.udp.subscribe`
  hear the same thing.
- **Why an assignment failed.** `ProviderBridge` overrides `assignServerOrSayWhy`: the provider
  thread answers an error with what `api_failure_of(exc)` read (`answer_error(id, code,
  api_code, retry_after_ms, message)`), and CrowdyCPP bounds it and keeps it
  (`last_assignment_failure`). `_ProviderServer` logs the bounded message, never `str(exc)`: a
  server's text can hold a line break.
- **`ApiFailure` is built in two places.** CrowdyCPP makes the connection's; `errors.py` makes
  the hub connection's and `api_failure_of`'s in Python, because `errors.py` imports no native
  code. `_server_text` and `retry_wait_ms` there must answer as CrowdyCPP's `serverText` and
  `retryWaitMs` do: `test_the_limits_are_crowdycpps` holds the wait to the native function,
  and a change to either side changes both.
- **Every wait on a server's hint goes through `retry_wait_ms`** (30 s at most):
  `CrowdyExecError.retry_after_ms` (`_retry_in_ms`, which also survives a number too long for
  `int()`), the kit runtime's hold, and `dropped_read_wait_ms` in `_dropped_read.py` for the
  Studio controller and `wait_for_mod_build`. A new wait on anything a server sent uses it.
- **A message shows no value that may be a secret.** `_gateway_name` (`domains/exec.py`) names
  a gateway by its scheme, host and port; `exec_gateway.py` catches `InvalidURI` (whose text
  is the whole URL, connect token included) and raises with no cause, and scrubs the token
  from any other socket error. Anything new that puts a caller's value or a server's text in
  a message describes it or bounds it first.
- **`managed_players.remove_many`** is CrowdyCPP's name (`removeMany`), as the 0.41.0 task
  asked, beside this repo's `delete`: CrowdyJS's `deleteMany` is classified
  `native-equivalent`, and there is no `delete_many` alias because this SDK aliases nothing.
  Rename it only together with the classification, the README and `MIGRATION.md`.
- **`AppTokenResponse.user_id`** is optional on purpose: `adopt_app_token` takes an answer an
  organization's server made, which may predate Application API v2.90.0. `_APP_TOKEN_FIELDS`
  selects `userId` for every token mutation (`domains/portal.py`, a CODEOWNERS path).
- **`tools/parity/classifications.toml` must hold no key twice.** A duplicate key is a TOML
  error that stops the whole gate, and it broke the 0.40.0 promotion. Before a push, load the
  file with `tomllib` and look for a key that two sections' edits both added.
- **The live suite** checks the sign-in's `userId` against the carry's, sends each carried
  player's keepalive and requires no refusal (step 5b, after the actors have reached the
  other server, because the first messages to a chunk can be refused while its permissions
  load), and its hub step dials the node type and key it is given
  (`CROWDY_FLEET_HUB_NODE_TYPE`, `_KEY`, `_METHOD`, and `CROWDY_FLEET_HUB_ORG_TOKEN` for a hub
  under another org token). Nobody has made a player without access live: the report is
  proven against the fake server.

## Releasing

The version lives in six places that `tests/unit/test_release_versions.py` holds together:
`[project].version`, `src/crowdypy/_version.py`, `uv.lock` (run `uv lock`), the README's
first `**vX.Y.Z` line, the first `## X.Y.Z` heading of `MIGRATION.md`, and
`docs/compatibility.md`. The branch always carries the bare `X.Y.Z`.

Merge to the tier branch, then tag the merge commit: `git tag -a dev/vX.Y.Z -m "CrowdyPy dev
vX.Y.Z" && git push origin dev/vX.Y.Z`. `release.yml` refuses a tag outside the branch it
names, a tag that is not the tree's version, and a default origin for another tier; then it
builds every wheel and the sdist, scans them, publishes `X.Y.Z.devN` (dev), `X.Y.ZrcN` (test)
or `X.Y.Z` (prod) to PyPI by trusted publishing, downloads the published wheel back to read
its origin again, and creates the GitHub release with the same files. PyPI publishing runs
only when the repository variable `PYPI_PUBLISHING` is `enabled` (it is, since 2026-10-01),
through the trusted publisher on PyPI project `crowdypy` (owner CrowdedKingdoms, repository
CrowdyPy, workflow `release.yml`, environment `pypi`). The first version there,
`0.4.0.dev1`, was uploaded by hand from the `dev/v0.4.0` release's assets before the
publisher existed; every later one comes from its tag. PyPI accepts a version once, so a
re-run takes the next N (`scripts/ci/resolve_pypi_version.py` reads what PyPI already has).

Merging a PR from the command line: `gh pr merge` fails its preflight on this org, so use
`gh api -X PUT repos/CrowdedKingdoms/CrowdyPy/pulls/<n>/merge -f merge_method=merge`.

## The Game Kit

`src/crowdypy/kit/` is the client half of `ckx_sdk::kit`, ported from CrowdyJS `src/kit/` (the
parity gate reads `src/kit/modules/` too since 0.12.0): one `KitRuntime` per kit, mirrors
(`mirror.py`), the typed modules (`modules/`, the genre starters' since 0.13.0; a keyword name
takes a trailing underscore, `pass_`, which the parity gate's `norm()` matches), `topology.py`
and `realtime.py`. It is async source
like the rest of the client, so `scripts/unasync.py` generates the blocking kit, and it may use no
asyncio beyond `asyncio.sleep`. **A push or reconnect handler never waits on a call.** The
blocking `ExecConnection` runs them on its reader thread, so a call made there would wait on a
reply only that thread can read: a mirror starts its resync with `run_detached`, which unasync
maps to `run_in_thread` (`run_soon` would become `run_now`, inline). Periodic work (a queue's
`watch`, a spectator's `run`) is a loop the game starts beside itself. The protocol is held to
ck-exec's golden record, `tests/fixtures/kit-protocol.json`, copied from CrowdyJS at the pin
(`test_fixture_provenance.py` and the vendored CrowdyCPP copy hold it):
`tests/unit/test_kit_protocol.py` replays each starter's script through a gateway that answers
only the next recorded step, with both clients.

## Teen safety (0.23.0, 0.24.0)

ck-api v2.60.0's gate and controls, ported from CrowdyJS 18.24.0: `client.safety` (the app
token), `client.moderation` (also `admin.moderation`; `moderate_safety`), the age, document and
Minecraft calls in `auth`, `apps`, `platform` and `portal`, and the refusal readers in
`errors.py`. Keep `age_requirement_not_met_of` a boolean: no refusal may name an age (decision
35 of the program), so it never surfaces `minimumAge` or `ageBracket`, as in CrowdyJS. 0.24.0
(ck-api v2.61.0, CrowdyJS 18.25.0) added `safety_moderator_required_of`,
`parental_consent_unavailable_of`'s `CrowdyParentalConsentUnavailable(reason)`,
`hasSafetyModerator`, `regionCode` and the claims' `region`. The operator-only roots
(`setTerritoryPolicy`, `exportPlayerData`, `childSafetyReports`, `eraseAccount`,

existing-account one an existing player (`docs/e2e-coverage.md`).

**The live teen safety suite never declares an age the platform refuses at sign-up or at
`record_player_age`** (the under-13 sign-up is opt-in, `CROWDY_E2E_UNDER13_SIGNUP=1`). Since
ck-api v2.61.0 such a refusal stops that address and user agent from signing up for 24 hours,
which on a shared machine stops every agent's suites. A managed refusal locks only that player,
and the suite uses fresh external ids. Each account a run registers spends the tier's shared
sign-up limit, so prefer existing accounts and say in the run's row what registered.

The Studio game editor (CrowdyJS 18.23.0) drives any `crowdypy.studio.DraftStore` the host's
`draft_store` factory returns. `GitHubDraftStore` (`studio/github_draft_store.py`) is CrowdyJS's
hosted backend ported, with its tests, over CrowdyPy's GitHub transport and a
`DraftOverlayStorage` (memory by default; the IndexedDB one is the browser's). CrowdyJS's
`crowdy-studio/draft/` is outside the parity gate's surface, so keep it in step by hand.

## Performance rules for the native binding

The replication system saturates the local network stack, so the binding
(`native/replication_binding.cpp`, `src/crowdypy/replication.py`) is held to these:

- No Python runs per datagram: receive, HMAC verify, decode and queueing stay in CrowdyCPP's
  thread, and Python receives batches.
- The network thread never takes the GIL. Anything it needs from Python (assignment, token
  refresh) is requested through a queue another thread serves, and it waits on a native
  condition, not on the interpreter.
- Sends are batched, and the GIL is released while a batch is encoded and sent.
- An asyncio loop is woken through `Config::onEventsReady` and a socket pair, never by a
  sleep-poll.
- While a World Stores session is attached it owns the connection's handlers. What its stores
  do not keep (audio, video, text, opcode 140, channel audio) is forwarded into the batch
  rows; voxel updates are forwarded only once Python watches them (`watch_voxels`, set by
  `session.on("voxel_update")`), since the chunk store already merges every one.
- Every change to the hot path reruns `benchmarks/bench_replication.py` and CrowdyCPP's
  `bench_send` on the same machine, and updates `benchmarks/README.md`.

## The native session and its chunk store

- The session is built without host election and with native write-back off. Both are
  GraphQL work the Python facade does on its timers.
- Its chunk source, `StagedChunks` in `native/session_binding.cpp`, only applies what the
  facade loaded. `ChunkStore.hydrate()` and `prune_beyond()` hand a chunk to it through
  `WorldSession.hydrate`, so stored edits follow CrowdyCPP's overlay rules: an edit the
  16x16x16 one-byte grid cannot hold goes to `ChunkData::overlay`.
- Do not write voxel types or states into the dense grid from Python. That bypasses the
  overlay, and the echo matching of local edits.
- Since 0.30.0 (CrowdyCPP 0.82.0) the native store paces and undoes edits; the binding turns its
