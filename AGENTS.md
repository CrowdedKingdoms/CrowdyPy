# CrowdyPy agent guidance

CrowdyPy is the public Python SDK for Crowded Kingdoms. Its API surface follows CrowdyJS
(the flagship) the way CrowdyCPP does; its replication hot path is CrowdyCPP's native core,
vendored and bound with nanobind. Trust the code over this file when they disagree, then fix
this file.

## Branches and tiers

GitHub default is **`prod`**. Work lands on `dev` through a pull request; `test` and `prod`
take merge-forward promotions (`dev` -> `test` -> `prod`) that an admin merges. Nobody can
push to the three branches directly, the admin included (`GH013: Repository rule violations
found` is the rule working). Dependabot targets `dev`.

**TIER ALIGNMENT (hard rule).** A CrowdyPy branch may only pin CrowdyJS and CrowdyCPP
commits that exist on the **same** tier branch of those repos (`dev`<->`dev`,
`test`<->`test`, `prod`<->`prod`). `scripts/ci/check_pin_tiers.py --from-ref` enforces it
in CI against the pull request's base. A promotion of CrowdyPy therefore waits for CrowdyJS
and then CrowdyCPP to reach that tier with the pinned commits.

**Identity surface.** A PR that touches the paths CODEOWNERS lists under `src/crowdypy/`
(auth, portal, pkce, session, auth_state, and their generated `_sync` twins) runs the Cursor
`security-review` subagent first, and the PR body carries its findings.

**Public repository.** Nothing internal goes in: no internal repository names, hostnames,
ports or environment variables. `scripts/ci/check_content_policy.py` scans the tree and the
built wheels and sdist against a denylist. Of the replication server, only the wire format
and the client authentication sequence are public.

## Pins

`pyproject.toml` records everything this tree was made against: `[tool.crowdypy.crowdyjs]`
(version and commit), `[tool.crowdypy.crowdycpp]` (version, tag, commit and the sha256 of
the vendored tree), `[tool.crowdypy.graphql]` (hashes of `schema.gql` and `operations/`) and
`[tool.crowdypy.published-sdl]`. CI re-derives each from the pinned commit, so a hand edit
anywhere downstream of a pin fails.

Moving the CrowdyJS pin (it must be on the same tier branch):

```bash
python scripts/schema_sync.py --crowdyjs ../CrowdyJS --ref <commit>   # schema, operations, pin
python scripts/codegen.py && python scripts/unasync.py
python tools/parity/parity.py --crowdyjs ../CrowdyJS --write docs/parity-matrix.md --strict
```

then port what changed, refresh `tests/fixtures/` from the same commit, and classify or
cover every new difference. Build CrowdyJS at the new pin (`npm ci && npm run build`) and run
`node tools/fixtures/player_host.mjs ../CrowdyJS`: it rewrites the player-host schemas and
their fixture, and `tests/unit/test_player_host.py` refuses either one from another commit. Moving the CrowdyCPP pin:

```bash
python scripts/vendor_crowdycpp.py --crowdycpp ../CrowdyCPP --ref <tier>/vX.Y.Z
```

CrowdyCPP's own CrowdyJS pin must equal CrowdyPy's (`--check` refuses otherwise).

## The default origin

`src/crowdypy/_default_origin.py` is generated per tier by the operator tooling and never
hand-edited: `dev` declares `dev`, `test` declares `test`, `prod` declares `prod`, so a
client built with no origin dials the tier its wheel was released for. **A promotion can
rewrite this file with no conflict and no mention**: git resolves a one-sided change
silently, so a clean `dev` -> `test` merge can carry `dev` onto `test`. Regenerate it for
the destination tier after every promotion. CI's `scripts/ci/assert_default_origin.py
--from-ref` judges the pull request base, the release guard judges the tag's tier, and the
release re-reads the published wheel.

## Gates

CI (`.github/workflows/ci.yml`) runs all of these; run them before pushing:

```bash
ruff check . && ruff format --check . && mypy
pytest tests/unit
python scripts/vendor_crowdycpp.py --check
python scripts/schema_sync.py --check
python scripts/codegen.py --check
python scripts/unasync.py --check
python tools/parity/parity.py --crowdyjs ../CrowdyJS --check docs/parity-matrix.md --strict
python scripts/ci/check_content_policy.py
python scripts/ci/check_pin_tiers.py --crowdyjs ../CrowdyJS --crowdycpp ../CrowdyCPP --tier dev
```

The parity gate is **strict** (since 0.4.0): every difference from CrowdyJS carries a
reviewed classification (`native-equivalent` or `browser-exclusion`), a stale or missing one
fails, and a `portable-gap` fails the build. Something new in CrowdyJS that CrowdyPy lacks is
ported in the same change that moves the pin; it is not parked as a gap.

## Releasing

The version lives in six places that `tests/unit/test_release_versions.py` holds together:
`[project].version`, `src/crowdypy/_version.py`, `uv.lock` (run `uv lock`), the README's
first `**vX.Y.Z` line, the first `## X.Y.Z` heading of `MIGRATION.md`, and
`docs/compatibility.md`. The branch always carries the bare `X.Y.Z`.

Merge to the tier branch, then tag the merge commit: `git tag -a dev/vX.Y.Z -m "CrowdyPy dev
vX.Y.Z" && git push origin dev/vX.Y.Z`. `release.yml` refuses a tag outside the branch it
names, a tag that is not the tree's version, and a default origin for another tier; then it
builds every wheel and the sdist, scans them, publishes `X.Y.Z.devN` (dev), `X.Y.ZrcN` (test)
or `X.Y.Z` (prod) to PyPI by trusted publishing, downloads the published wheel back to read
its origin again, and creates the GitHub release with the same files. PyPI publishing runs
only when the repository variable `PYPI_PUBLISHING` is `enabled`, which the operator sets
once the PyPI trusted publisher (workflow `release.yml`, environment `pypi`) is registered.

Merging a PR from the command line: `gh pr merge` fails its preflight on this org, so use
`gh api -X PUT repos/CrowdedKingdoms/CrowdyPy/pulls/<n>/merge -f merge_method=merge`.

## Performance rules for the native binding

The replication system saturates the local network stack, so the binding
(`native/replication_binding.cpp`, `src/crowdypy/replication.py`) is held to these:

- No Python runs per datagram: receive, HMAC verify, decode and queueing stay in CrowdyCPP's
  thread, and Python receives batches.
- The network thread never takes the GIL. Anything it needs from Python (assignment, token
  refresh) is requested through a queue another thread serves, and it waits on a native
  condition, not on the interpreter.
- Sends are batched, and the GIL is released while a batch is encoded and sent.
- An asyncio loop is woken through `Config::onEventsReady` and a socket pair, never by a
  sleep-poll.
- Every change to the hot path reruns `benchmarks/bench_replication.py` and CrowdyCPP's
  `bench_send` on the same machine, and updates `benchmarks/README.md`.
